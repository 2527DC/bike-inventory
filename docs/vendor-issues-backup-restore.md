# Vendor & Vendor Issue backup — column and data-type map

Companion to the generated SQL file. For each table: every column in the current
`prisma/schema.prisma`, its Prisma type, the PostgreSQL type it becomes, the type the
backup (`complete_database_backup.sql`, pg_dump 17.6) had for it, and whether the value
is carried across. Generated by `extract-vendor-backup.js`; do not hand-edit — regenerate.

## How the SQL was shaped

- The backup's `INSERT`s are **positional** (`INSERT INTO t VALUES (…)`) — their meaning depends
  on the OLD table's column order. The generated file names every column explicitly, in the
  current schema's order, so it pastes correctly regardless of order.
- Every statement ends `ON CONFLICT DO NOTHING`, so the file can be pasted twice without error
  and never overwrites a row that already exists (by id, or by any unique key such as
  `Vendor.name`, `Vendor.code`, `VendorIssue.issueNo`, `User.email`).
- Enum columns (`IssueType`, `IssueStatus`, `IssuePriority`, `IssueSource`) have **identical value
  sets** on both sides; the text literal casts to the enum on insert.
- `timestamp(3) without time zone`, `text[]` and `double precision` are the same on both sides.

## Regenerating the SQL, and where the files live

The SQL file holds real data — GSTINs, phone numbers — so it lives
**outside the repository**, next to the backup it came from, and must never be committed or
pasted into a chat or a ticket:

```
F:\bharath  Cycle\complete_database_backup.sql        ← the full pg_dump (source, read-only)
F:\bharath  Cycle\vendor-and-issues-backup.sql        ← the generated file to paste
```

To regenerate (for example after a schema change to any of the four tables), from the repo root:

```
node scripts/db/extract-vendor-backup.js "F:\bharath  Cycle\complete_database_backup.sql" prisma\schema.prisma "F:\bharath  Cycle\vendor-and-issues-backup.sql" docs\vendor-issues-backup-restore.md --user=cmt8hr7hq00ecw2n8gymzo7t5
```

`--user=<id>` points every issue/note author at that one existing user and inserts no user rows;
without it, the original authors are carried across as inactive users. It rewrites both the SQL and
this document from the current `schema.prisma`. If the schema gained a required column the backup
does not have, it stops and names the column instead of emitting SQL that would fail on paste.

## Pasting it

1. The target must be up to date (`npx prisma migrate status`) and the user `cmt8hr7hq00ecw2n8gymzo7t5` must exist in its `User` table.
2. `psql "<url>" -v ON_ERROR_STOP=1 -f "F:\bharath  Cycle\vendor-and-issues-backup.sql"`, or paste
   the whole file into the Supabase SQL editor. It is one transaction: it all lands or none of it.
3. Verify with the `SELECT` at the bottom of the file — expect 83 vendors, 18 contacts,
   183 issues, 289 notes.
